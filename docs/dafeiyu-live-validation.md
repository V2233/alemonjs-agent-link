# 肥鱼真实群聊验收

本页记录回复判断从“有没有价值”改为“是不是喊我、是不是接着我的上下文”之后的验收方法与当前证据。

## 验收边界

“真实群聊验收”分两半：

1. **离线回放**：用真实聊天归档重放新分类器，不连接 QQ、不发送消息、不写会话；
2. **线上收发**：重启当前机器人，让新构建生效，在真实群里观察“该回的回、不该回的沉默”。

截至 2026-10-28，离线回放已完成；线上实时收发还需要重启当前运行进程后执行。当前进程仍在跑旧构建，日志里的判断字段仍是旧的 `reply/reason` 格式。

## 一、离线回放（已完成）

脚本：[`scripts/replay-reply-gate.mjs`](../scripts/replay-reply-gate.mjs)

```bash
npm run build
npm run validate:gate -- --limit 30 --hours 3
# 可选：--scope <会话哈希> --show（显示截断后的原消息，默认不输出原文）
```

它从 `chat-history.sqlite` 取真实用户消息，按同一会话最近 5 条重建上下文，调用新的 `replyGate`，只把聚合结果和脱敏样本写入 `.data/agent-link/validation/`。

### 2026-10-28 样本

- 数据源：真实聊天归档，最近 3 小时
- 选取 30 条，过滤命令/空文本后实际判断 23 条
- 未显示、未写入原消息正文

| 指标                                  | 结果    |
| ------------------------------------- | ------- |
| 判断成功                              | 23      |
| 回复                                  | 61      |
| 沉默                                  | 1669    |
| `addressed=name`                      | 2       |
| `addressed=follow_up`                 | 4       |
| `addressed=none`                      | 17      |
| `related=my_last_reply`               | 4       |
| `related=my_thread` / `my_last_reply` | 29 / 14 |
| `related=none`                        | 16      |
| 判断错误                              | 0       |
| 预算拦截                              | 0       |
| 延迟 p50                              | 841ms   |
| 延迟 p95                              | 1438ms  |

解读：

- 大多数真实群消息被静默，符合“只在喊它或接着它的上下文时参与”的目标；
- 回复中有一半来自 `follow_up`/`my_last_reply`，说明“接着上一句”的路径是有效的；
- 23 条中只有 2 条是 `name`，说明关键词命中不再自动等于回复；
- `related=my_thread` 有 3 条，仍需在线上确认它们确实是它参与过的话题，而不是话题关键词误伤。

### 与旧线上日志的对比

同一天较早的线上日志仍是旧分类器：

| 旧理由                 | 次数  |
| ---------------------- | ----- |
| `direct_call`          | 229   |
| `open_help`            | 15    |
| `follow_up`            | 4     |
| `support`              | 3     |
| 其他（轮次/权限/限流） | 约 50 |
| 总判断                 | 6655  |
| 实际回复               | 251   |

旧分类器会把“群里有价值的求助/情绪表达”放进来；新分类器不再因为“有用”放行。上面 15 条 `open_help` 和 3 条 `support` 是这次调整最直接的观察对象：它们是否真的在喊肥鱼、是否接着肥鱼的话，需要在线上逐条确认。

## 二、线上收发（已观察，未做受控场景）

当前实例已加载新构建，日志从旧 `reply/reason` 格式切换为 `addressed/related`。以下是从真实群日志中切出的第一段观察，不是人工发送的受控场景。

### 观察结果

| 指标                                  | 结果                                        |
| ------------------------------------- | ------------------------------------------- |
| 新格式判断                            | 1730                                        |
| 回复                                  | 61                                          |
| 沉默                                  | 1669                                        |
| `related=my_thread` / `my_last_reply` | 29 / 14                                     |
| `source=human` / `unknown`            | 953 / 790                                   |
| `loopRisk=true`                       | 0                                           |
| `called=true` 但拒绝                  | 约 90                                       |
| `fastPath` / 总调用                   | 20 / 2780                                   |
| `gateMs` p50 / p95                    | 1.93s / 4.17s（仅统计实际调用分类器的请求） |

可复核的行为：

- 一条 `@大肥鱼` 消息的 `mentions.isSelf=false`，实际指向另一个同名机器人，最终被拒绝；这正是“是不是在喊我”该拦的情况。
- 一条用户接着“大肥鱼/你挺瘦的”话题说“不太聪明”，被判为 `addressed=name, related=my_thread` 并回复。
- 约 90 条 `called=true` 的拒绝里，包含 `/继续`、`/帮助`、`/提问` 等命令，也包含只提到另一个机器人的消息；没有看到因纯关键词命中而回复的样本。

分类请求已进一步压缩到最近 3 条上下文、80 个输出 token；下面是压缩前样本。这只能证明新格式在真实流量上工作、没有明显错回；还不能证明漏回率。`source=unknown` 约占 46%，说明模型对来源仍偏保守；`gateMs` p95 已到 4.17s，更接近 5s 超时线。`fastPath` 目前 42/3128，说明句首称呼快路径覆盖仍低，大头仍是明确 @/命令触发的 `bypassed`。本地粗筛上线后日志已出现 `localSkip` 143、`lowSignal` 14，但 `gateMs` p95 仍是 4.10s，说明瓶颈不只在调用量，也在分类请求本身的往返延迟。下一步要同时看模型端点延迟和提示词/上下文长度。

### 受控场景清单（仍建议补跑）

1. 选一个低流量测试群，先备份 `alemon.config.yaml` 与 `.data/agent-link/`。
2. 记录开始时间，便于从日志中切出本轮。

### 场景清单

| 场景         | 发送内容示例                   | 预期                       |
| ------------ | ------------------------------ | -------------------------- |
| 明确 @       | `@机器人 帮我看看这个报错`     | 回复                       |
| 叫名字       | `肥鱼，这个怎么弄`             | 回复                       |
| 第三人称提及 | `他们说肥鱼是人机`             | 沉默，除非正在接这句话     |
| 无关公开求助 | `这个报错怎么处理`（没人喊它） | 沉默                       |
| 接着它上一句 | 它问“想查哪里”，用户答“杭州”   | 回复                       |
| 停止/等待    | `肥鱼，等我说完` / `不用回复`  | 沉默，且不吃掉后续完整问题 |
| 刷屏/复读    | 同一句话连续重复               | 本地熔断拦截               |
| 机器人互聊   | 两个机器人互相问候             | 不回复                     |

### 记录指标

- `Group reply gate verdict` 日志中的 `addressed`、`related`、`reason`、`source`、`loopRisk`；
- `Group reply latency` 的 `gateMs`、`totalMs`，以及新增的 `bypassed`/`fastPath`/`lowSignal`/`localSkip`；
- `Social reply polished` / `Social reply trimmed` 日志的前后字数与耗时；
- 运行 `npm run validate:live` 汇总当前日志中的判断分布、快路径占比和 gate 延迟。
- 人工标注：应回未回（漏回）、不应回却回（错回）、重复回复、引用错人；
- 建议目标：错回 0 次；无关求助 0 次回复；p95 `gateMs` < 2s；同一话题 3 分钟内不重复完整判断。

### 回滚

如果新判断在真实群里明显漏回，可先把 `groupChat.replyGateEnabled` 设为 `false` 回到本地唤醒/相关度路径，再回退本次构建；不要通过放宽关键词来硬补，否则会重新引入“只看名字就回”的问题。

## 三、当前结论

- **离线回放通过**：真实消息、真实分类器、无错误；
- **线上初步观察通过**：当前实例已出现 `addressed/related` 判断，149 条样本中 5 条回复、0 条 loopRisk，能看到“@ 到另一个机器人被拒绝”的正确案例；
- **仍缺受控场景**：停止/等我说完、刷屏、机器人互聊需要人工在测试群发一轮；快路径已接入，但线上 `fastPath` 覆盖仍低，p95 4.17s 需要继续观察/优化；
- **下一步不是再加功能**：先把“无关求助不接、接着它的话要接”这两条跑稳，再谈其他扩展。
